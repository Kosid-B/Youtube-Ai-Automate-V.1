## ทำไมต้องแยกชั้นขนาดนี้

OpenAI ประกาศเลิก Videos API + `sora-2` + `sora-2-pro` วันที่ **24 ก.ย. 2569**
โดยแจ้งล่วงหน้าแค่ 6 เดือน ผู้ให้บริการวิดีโอเปลี่ยนเร็วกว่าโมเดลภาษามาก

ถ้าตรรกะธุรกิจเรียก SDK ของเจ้าใดเจ้าหนึ่งตรง ๆ วันที่เขาปิดเราต้องรื้อทั้งเส้นทาง
ไม่ใช่แค่เปลี่ยน adapter

### งานสร้างวิดีโอเป็น "งานยาว" ไม่ใช่ request-response

ต่างจาก provider layer อื่นในโปรเจคนี้ (`llm.ts`, `tts`, `image-gen`) ที่เรียกแล้วได้ผลเลย

```
generate()  →  providerJobId        (ทันที)
getStatus() →  running / done / failed   (ถามเป็นระยะ นาที ไม่ใช่วินาที)
getResult() →  bytes
```

เขียนเป็นฟังก์ชันเดียวที่รอจนเสร็จจะ**ค้าง worker ทั้งตัว** และ retry ทีไรก็
เสียเงินสร้างใหม่ทุกครั้งเพราะไม่มี id ให้กลับไปถาม

## นโยบายการเลือกเจ้า (Routing)

| นโยบาย | เริ่มจากระดับ | ใช้เมื่อไร |
|---|---|---|
| `cheap` | lite | ทำหลายชิ้นเพื่อคัด |
| `fast` | fast | คุณภาพกลาง ราคากลาง |
| `quality` | quality | ชิ้นที่จะเอาไปยิงแอดจริง |
| `auto` | quality แล้วลดลง | เอาดีที่สุดเท่าที่งบต่อชิ้นไหว |

**ตัดสินจาก 4 อย่าง ตามลำดับ**
1. เจ้าไหนตั้งคีย์ไว้บ้าง (ไม่มีคีย์ = ไม่มีอยู่)
2. ระดับที่นโยบายขอ
3. งบต่อชิ้น (`MAX_VIDEO_COST_USD`)
4. ราคาถูกสุดในบรรดาเจ้าที่เข้างบ

**ลดระดับทีละขั้น ไม่ร่วงไปถูกสุด** — งบ $1 กับคลิป 8 วินาที ยังจ่าย fast ($0.80) ไหว
การไปเอา lite ($0.40) ทั้งที่งบพอ คือลดคุณภาพเกินจำเป็น

**ลดแล้วต้องบอกเสมอ** — `Route.downgraded` ติดธงไว้ให้ UI แสดง
เปลี่ยนคุณภาพเงียบ ๆ คือหลอกผู้ใช้

**ต้อง deterministic** — อินพุตเดียวกันต้องได้เจ้าเดียวกันเสมอ ไม่งั้นผู้ใช้เห็นราคา
ตอนกดแล้วโดนอีกราคาตอนจ่าย (ไม่มีการสุ่ม ไม่อ่านเวลา ไม่ยิงเน็ตใน `router.ts`)

## ด่านคุมงบ

```
MAX_VIDEO_COST_USD          เพดานต่อคลิปหนึ่งชิ้น (ค่าเริ่มต้น 5)
MAX_VIDEO_DURATION_SECONDS  ความยาวสูงสุดที่ขอได้ (ค่าเริ่มต้น 30)
```

**ทำไมต้องมีทั้งที่มีระบบเครดิตอยู่แล้ว** — เครดิตกันได้แค่ "จำนวนงาน" ไม่ได้กัน
"ขนาดของงานแต่ละชิ้น" บั๊กที่ส่งความยาวผิดหน่วยไปหนึ่งครั้ง (8 → 800) ทำเงินหาย
สิบเท่าในคำสั่งเดียวโดยเครดิตไม่รู้สึกอะไร

**ห้ามเชื่อราคาจากเบราว์เซอร์เด็ดขาด** — `schema.ts` ไม่มีช่องราคา ช่องชื่อเจ้า
หรือช่องชื่อรุ่นให้ผู้ใช้กรอก ผู้ใช้ส่งได้แค่ "อยากได้อะไร" ราคาคิดจากฝั่งเราเท่านั้น

**แยก `estimated_cost_usd` กับ `actual_cost_usd`** — ค่าประมาณคือตัวเลขเดียวที่มี
ตอนตัดสินใจ ส่วนบิลจริงมาทีหลังและไม่เท่ากัน เอาค่าประมาณไปคิดกำไรขาดทุน
= ตัวเลขธุรกิจผิดทั้งชุด

**Runway: ไม่รู้ราคา = ไม่ให้ใช้** — Runway คิดเป็นเครดิตซึ่งราคาต่อเครดิตต่างกัน
ตามแพ็ก `estimateCostUsd()` จึงโยน error เมื่อไม่ได้ตั้ง `RUNWAY_USD_PER_SECOND`
ตั้งใจให้เป็นแบบนั้น เดาราคาแล้วปล่อยผ่าน = งบบานโดยไม่มีใครรู้

## ความปลอดภัย

### RLS

ทุกตารางเปิด RLS และใช้กติกาเดียวกัน: **เห็นเฉพาะองค์กรที่ตัวเองเป็นสมาชิก**

```sql
using (is_org_member(org_id))                                    -- อ่าน
using/with check (has_org_role(org_id, ['owner','admin','editor'])) -- เขียน
```

⚠️ **ใช้ `org_id` ไม่ใช่ `workspace_id`** — repo นี้ใช้ `organizations` / `org_members` /
`is_org_member()` ทั้งระบบ ใช้ `workspace_id` = ทุก policy อ้างฟังก์ชันที่ไม่มีอยู่

⚠️ **`WITH CHECK` ไม่ใช่ของประดับ** — policy ที่มีแต่ `USING` ยอมให้แก้ `org_id`
ของแถวตัวเองให้ไปโผล่ในองค์กรอื่นได้ ต้องมีทั้งคู่

⚠️ **ไม่เชื่อ `org_id` ที่เบราว์เซอร์ส่งมา** — server action หา org จากสมาชิกภาพของ
session เสมอ (`actor()` ใน `actions.ts`) เพราะการเขียนต้องใช้ service client
ซึ่งข้าม RLS ถ้ารับ org_id จากเบราว์เซอร์แล้วเอาไปเขียน ชั้นกันนั้นหายไปทั้งชั้น

## AI Marketing Director

```
video_projects.objective        "หาลูกค้าโรงงาน SME ที่กำลังจะทำ ISO"
      ↓  งาน video_plan (worker/handlers/video-plan.ts)
ICP → ความเจ็บ → คำสัญญา → hook → บทพูด → CTA → สตอรีบอร์ด
      ↓
video_scripts + storyboard jsonb [{ shot, seconds, prompt, voiceover }]
      ↓  กดช็อตที่หน้าเว็บ → คำสั่งภาพเด้งลงฟอร์ม
video_generations               (เส้นทางเดิมทั้งหมดจากตรงนี้)
```

**ทำไมต้องไล่ตามลำดับ ไม่กระโดดไปที่ hook เลย** — hook ที่ดีคือประโยคที่พูดกับ
"คนคนหนึ่ง" เรื่อง "ความเจ็บข้อหนึ่ง" ข้ามสองขั้นแรกไปจะได้ hook ที่ฟังดูดีแต่ไม่โดนใคร
ซึ่งเป็นคลิปโฆษณาส่วนใหญ่ในโลก

### เข้าคิว ไม่เรียกตรง

วางแผนใช้เวลาเป็นนาที (`effort: 'high'` + สตอรีบอร์ดหลายช็อต) เกินเวลาที่ server action
มีให้บนโฮสต์ส่วนใหญ่ · เรียกตรงจะได้ timeout ที่ไม่บอกอะไร ทั้งที่โมเดลยังทำงานอยู่
และคิดเงินไปแล้ว

`video_plan` เป็น job kind ใหม่ — `jobs.kind` เป็น `text` จึงไม่ต้อง migrate

### สองภาษาในสตอรีบอร์ด โดยเจตนา

| ช่อง | ภาษา | เพราะ |
|---|---|---|
| `prompt` | อังกฤษ | Veo/Runway ฝึกด้วยข้อมูลอังกฤษเกือบทั้งหมด ตอบสนองดีกว่ามาก |
| `voiceover` | ไทย | คนดูเป็นคนไทย |

`prompt` บรรยาย "สิ่งที่กล้องเห็น" อย่างเดียว — ห้ามสั่งใส่ข้อความบนจอ
เพราะโมเดลวิดีโอเขียนตัวหนังสือไทยไม่ได้ (ได้ออกมาเป็นอักขระมั่ว)

### ตัวเลขที่ไม่มีที่มา — ด่านที่สำคัญที่สุดของชั้นนี้

โมเดลเติมตัวเลขที่ "ฟังดูสมเหตุสมผล" ให้เองเป็นเรื่องปกติ แม้จะสั่งห้ามใน prompt แล้ว
และตัวเลขที่ฟังดูสมเหตุสมผลคือตัวเลขที่คนอ่านผ่านโดยไม่เอะใจ — อันตรายกว่าตัวเลข
ที่ผิดจนสังเกตได้ เพราะมันไปโผล่ในโฆษณาจริงได้ (โฆษณาเกินจริง = ผิดกฎหมายไทย)

`unverifiedClaims()` จับตัวเลขที่ "ฟังเหมือนคำโฆษณา" แล้วเทียบกับบรีฟ:

| จับ | ไม่จับ | เพราะ |
|---|---|---|
| `40%` · `฿500,000` · `3 เท่า` · `500 โรงงาน` | `3 ข้อ` · `2 นาที` | เลขเล็กเป็นโครงประโยค ไม่ใช่คำกล่าวอ้าง |
| | `ปี 2569` | ปีไม่ใช่คำกล่าวอ้าง |

จับหมดทุกตัวเลขจะได้คำเตือนเยอะจนไม่มีใครอ่าน — **คำเตือนที่ถูกมองข้ามทุกครั้ง
คือคำเตือนที่ไม่มีอยู่** และมันจะพาคำเตือนข้ออื่นตายไปด้วย

### แผนที่มีปัญหาไม่ถูกทิ้ง

`planProblems()` คืนรายการปัญหา ไม่ throw · handler บันทึกแผนแล้วเลื่อนสถานะเป็น
`scripted` ตามปกติ · หน้าเว็บแสดงคำเตือน **เหนือ** ปุ่มสั่งสร้าง (ใต้ปุ่ม = หลังจ่ายเงินแล้ว)

ทิ้งทั้งแผนเพราะช็อตเดียวยาวเกินคือเผาเงินที่จ่ายให้โมเดลไปแล้วทิ้ง

**คำเตือนไม่ถูกเก็บลงตาราง** — คำนวณใหม่จากแถวทุกครั้งที่เปิดหน้า (`planProblems` บริสุทธิ์)
เก็บลงตารางแล้ววันที่กติกาเปลี่ยน แผนเก่าจะโชว์คำเตือนชุดเดิมค้างไว้ทั้งที่ไม่ใช่ปัญหาแล้ว
หรือแย่กว่า: ไม่โชว์ปัญหาใหม่ที่เพิ่งกลายเป็นปัญหา

### ICP / ความเจ็บ / โน้ต เก็บไว้หัวบท

`video_scripts` ไม่มีคอลัมน์ให้ · `scriptWithContext()` ฝังสามบรรทัดนี้ไว้หัว `script`
แล้ว `planFromRow()` อ่านกลับ (มีเทสต์ round-trip บังคับให้สองตัวนี้เดินสวนกันได้เป๊ะ)

- **ICP กับความเจ็บ** ทิ้งไปแล้วรอบหน้าที่มีคนแก้บท เขาจะแก้โดยไม่รู้ว่ากำลังพูดกับใคร
  แล้วบทจะค่อย ๆ กลายเป็นกลาง ๆ จนไม่โดนใคร
- **โน้ตของผู้ใช้** เป็นส่วนหนึ่งของบรีฟ ทิ้งแล้วตัวเลขที่ผู้ใช้พิมพ์มาเองจะถูกเตือนว่า
  "ไม่มีที่มา" ทุกครั้งที่เปิดหน้า ซึ่งเป็นคำเตือนปลอม

### ค่าคงที่

| ค่า | เท่าไร | เพราะ |
|---|---|---|
| `SHOT_SECONDS` | 3–8 (เป้า 6) | ผู้ให้บริการสร้างได้ครั้งละ ~8 วินาที · สั้นกว่า 3 คนดูยังไม่ทันเห็น |
| `MAX_SHOTS` | 8 | หนึ่งช็อต = เงินหนึ่งก้อน · แผน 20 ช็อตอ่านแล้วดูดี แต่คลิปเดียว $16 |
| `HOOK_SECONDS` | 3 | เวลาที่มีจริงก่อนคนเลื่อนผ่าน |
| `HOOK_WARN_CHARS` | 56 | เผื่อ 1 วินาทีจากเป้า 42 — เตือนทุกแผน = ไม่มีใครอ่าน |

ความยาวรวมต่อแพลตฟอร์ม: Shorts/Reels/TikTok 20 วินาที · Facebook/เว็บ 30 วินาที

## วงจรชีวิตของงานหนึ่งชิ้น (ครบวงแล้ว)

```
server action สั่ง        actions.ts generateVideo()
      ↓                   บันทึกแถวก่อนสั่งเสมอ (สลับลำดับ = เงินหายเงียบ)
dispatchGeneration()      ได้ provider_job_id → status 'running'
      ↓
enqueueJob video_poll     ล้มตรงนี้ไม่ทำให้คำขอล้ม — เงินออกไปแล้ว
      ↓
worker/handlers/video-poll.ts
      ├─ ยังไม่จบ  → DeferJobSignal (คืนงานเข้าคิว ไม่ยึด worker)
      ├─ เกิน 30 นาที → failed + error_code 'timeout'
      │                 ข้อความต้องบอกว่าเงินอาจออกไปแล้ว ไม่ใช่แค่ "ไม่สำเร็จ"
      └─ เสร็จ     → getResult() → upload → ค่อยเขียน output_storage_path
      ↓
/api/video/<id>/download  signed URL อายุ 5 นาที ผ่าน client ที่ผูก session
```

สองข้อที่ห้ามสลับ:

1. **อัปไฟล์ก่อนบันทึกพาธ** — สลับแล้วถ้าอัปล้ม แถวจะชี้ไปไฟล์ที่ไม่มีอยู่
   และ retry รอบหน้าจะเห็น `output_storage_path` แล้วข้ามไป คลิปหายถาวร
2. **`defer_job` ลด `attempts` ลงหนึ่ง** — การวนถามจึงไม่กินโควตา retry
   ซึ่งแปลว่าวนได้ไม่รู้จบถ้าผู้ให้บริการค้าง จึงต้องมีเพดานเวลาของเราเอง

| ตัวแปร | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `VIDEO_POLL_INTERVAL_SEC` | 20 | ถามซ้ำทุกกี่วินาที |
| `VIDEO_POLL_DEADLINE_MIN` | 30 | เลิกรอหลังกี่นาที |

## ที่ยังไม่ได้ทำ

- **ยังไม่ได้ยิงกับ API จริงทั้งสองเจ้า** — ไม่มีคีย์ในเครื่องพัฒนา
  รูปแบบคำขอ/คำตอบอ้างจากเอกสาร เทสต์ทั้งหมดใช้ mock
  เรียกครั้งแรกให้ดู log ว่าตรงไหม โดยเฉพาะชื่อฟิลด์ของ operation
- **Rate limiter อยู่ในหน่วยความจำ** — ใช้ได้จริงเมื่อรัน instance เดียว
  บน Vercel หลาย instance ตัวนับแยกกัน เพดานจริง = เพดานที่ตั้ง × จำนวน instance
  เปลี่ยนเป็น Redis เมื่อขึ้น production จริง (ชั้นนามธรรมพร้อมแล้ว)
- **`video_generation_metrics` ยังไม่มีใครเขียน** — รอเชื่อมกับแพลตฟอร์มปลายทาง
- **Director ยังไม่เรียนรู้จากผลงาน** — วางแผนจากบรีฟอย่างเดียว ยังไม่ได้อ่าน
  `video_generation_metrics` ว่า hook แบบไหนของ "องค์กรนี้" ได้ผลจริง
  (สายคลิปเล่าเรื่องมี `lib/content-feedback.ts` ทำแบบนี้อยู่แล้ว — ยกรูปแบบมาใช้ได้
  เมื่อมีข้อมูลผลวัดพอ)
- **หนึ่งโปรเจคหนึ่งแผน** — ยังวางแผนใหม่หรือขอหลายเวอร์ชันมาเทียบกันไม่ได้
  ซึ่งเป็นสิ่งที่คนทำโฆษณาจริงต้องการ (ทำสามอันแล้วคัด) · ตารางรองรับหลายแถวต่อโปรเจค
  อยู่แล้ว ติดแค่ปุ่มกับการเลือกว่าจะใช้แถวไหน
